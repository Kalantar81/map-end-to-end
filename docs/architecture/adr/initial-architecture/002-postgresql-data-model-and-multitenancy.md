# ADR-002 — PostgreSQL + TypeORM, data model and the multi-tenancy foundation

- **Status:** Accepted
- **Date:** 2026-09-24
- **Author:** architect
- **Source of truth:** `docs/architecture/initial-architecture.md` — §1, §2.2, §2.4 (OQ #1, #6, #7, #9–#11), §2.5 (A2, A3), §3, §4, §6
- **Scope:** `back/` persistence layer (`organizations`, `users`, `configurations`), `infra/docker-compose.yml`

## Context

Nothing exists on the persistence side yet (§1): `back/` is a NestJS 10 scaffold with no database. The PRD
names MongoDB but also requires that every user belongs to an organization (US-1a) and warns that the
configuration schema will grow (OQ #1). Three questions had to be answered before backend work starts:
which store, whether an organization is a table or a field (OQ #9–#11), and where the growing configuration
payload lives.

## Decision

1. **PostgreSQL 16** via `@nestjs/typeorm@10.0.2` + `typeorm@^0.3` + `pg@^8`, entities declared with decorators
   so they plug straight into Nest DI. Connection from `@nestjs/config` + `.env` (`DATABASE_URL`, required and
   validated at boot); `infra/docker-compose.yml` runs `postgres:16` locally plus a separate `config_viewer_test`
   database for e2e (OQ #7).
2. **Three tables** (§6.1): `organizations` (`id`, unique `name`, unique lowercase-kebab `slug`, timestamps),
   `users` (`id`, unique lowercase `username`, `passwordHash` with **`select: false`**, `displayName`,
   **required** `organizationId` FK → `organizations.id` `ON DELETE RESTRICT`, timestamps) and `configurations`
   (`id`, unique `name`, optional `description`, `settings` **jsonb**, timestamps).
3. **Organizations are a real table with a foreign key** — the multi-tenancy foundation (OQ #11). Two seeded
   organizations, users split 5/5 (OQ #9, #10, §6.3). **No org filtering of configurations in the MVP:** a
   configuration is a global catalogue entity (A3), and the future increment is additive — a
   `configuration_organizations` join table + one query filter + one guard. `orgId` is already carried in the JWT
   so that increment needs no token change.
4. **The configuration payload lives in `settings` jsonb**, MVP shape `{ mapLib: 'openlayers' | 'arcgis' }`
   (`@Check("(settings->>'mapLib') IN ('openlayers','arcgis')")` is the only guard against a malformed seed,
   since the MVP has no write endpoints). Normative extensibility rule: future configuration fields are added
   **inside `settings`**, clients ignore unknown `settings` keys, `settings.mapLib` stays required (§5.7).
5. **Conventions:** UUID v4 primary keys generated by PostgreSQL — TypeORM configured with
   `uuidExtension: 'pgcrypto'`, because its default `uuid-ossp` needs a superuser. Passwords `bcrypt` cost 10
   (OQ #6). `username` case-insensitivity is enforced by normalisation (`@Transform` in the login DTO +
   `@BeforeInsert()` on the entity) on top of a plain `unique` constraint, not by an expression index or `citext`.
   Indexes: unique on `organizations.name`/`slug`, `users.username`, `configurations.name`; non-unique on
   `users.organizationId`. Entities are never returned directly — DTO-mapped responses only (§9).
6. **Schema management:** `synchronize` only outside production; versioned TypeORM migrations
   (`data-source.ts` + CLI scripts) before any shared environment.

## Alternatives considered

| Alternative | Why rejected (§3) |
|---|---|
| MongoDB + Mongoose (**as named in the PRD**) | The data is relational — `users → organizations` with a required foreign key (US-1a) — and the flexible part, `settings`, fits a `jsonb` column. This is a **deliberate deviation from the PRD**; product-manager must update the PRD. |
| Prisma + PostgreSQL | Adds a separate schema file and code generation outside Nest's decorator model; TypeORM plugs into Nest DI directly. |
| In-memory store | Cannot satisfy the "real data in the database" success metrics. |
| `organizationName` string on the user | Cheaper today, but forces a data migration precisely where the PRD says migration cost is the reason to design now (US-1a). |
| Full tenant isolation (database per tenant) | Heavy multi-tenancy for a product with 2 seeded organizations and no filtering yet. |
| Flat `mapLib` column on the configuration | Mixes identity/metadata with payload, so every future field widens the root DTO. |
| Free-form jsonb payload without DTO validation | Throws away validation and Swagger typing. |
| Versioned schema registry for `settings` | Over-engineering for one field. |

## Consequences

**Gains**

- The user→organization relationship already exists, so org-scoped visibility is an *additive* change, not a migration.
- Adding configuration fields later touches `settings` only: one settings type, one DTO, one UI block.
- `select: false` on `passwordHash` plus DTO-only responses make a password-hash leak structurally unlikely.
- One process + one database: cost of ownership is docker-compose and nothing else.

**Costs accepted**

- **A documented deviation from the PRD** (MongoDB → PostgreSQL) that has to be reconciled by product-manager.
- **Developers now need a running PostgreSQL and a `.env`** — the operational surface grew from zero.
- **No org filtering yet:** any logged-in user sees all configurations. This is a PRD-sanctioned simplification
  (US-2) and **must not be read as an authorization model**.
- No pagination, caching, read replicas or indexes beyond uniqueness/lookup indexes — justified by A2 (tens of
  users, <100 configurations) and revisited only when that assumption breaks.
- `jsonb` gives up column-level typing in the database: correctness of `settings` rests on the DTO validation and
  the single `@Check` constraint.
- The `typeorm` 0.3 line is what `@nestjs/typeorm@10` declares (0.3.x now sits on the `legacy` dist-tag). Upgrade
  path when needed: `@nestjs/typeorm@11` + `typeorm@1` (§2.3).
